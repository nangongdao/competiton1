# 多平台内容发布工具 Demo 演示台本

## 1. 演示目标

用 5 到 8 分钟说明三件事：

1. 创作者多平台同步发布为什么痛。
2. 本项目如何把一份内容自动适配成公众号、知乎、B站、小红书、掘金、博客园、CSDN 可发布内容。
3. 本项目不仅能模拟发布，还支持公众号官方 API 发布，以及基于 Playwright 的真实网页端自动化分发。

## 2. 演示前准备

提前启动：

```bash
npm install
npm run dev
npm run runner
```

可选：

```bash
npm run server
```

演示环境建议：

- 浏览器里打开 Web 工具：`http://localhost:5176`
- 如果演示真实网页自动化，提前让知乎、B站、小红书、掘金、博客园、CSDN 在本机 Chromium 登录好
- 如果演示公众号真实发布，提前确认 `packages/server/.env` 已配置公众号凭据

## 3. 开场话术

“很多内容创作者都会遇到同一个问题：同一篇内容发到公众号、知乎、B站、小红书、掘金、博客园、CSDN 时，每个平台格式要求都不一样。公众号要内联样式、知乎对公式和富文本有自己的处理、B站专栏对 HTML 子集有限制、小红书又更偏纯文本和话题风格，掘金、博客园和 CSDN 则原生支持 Markdown。手工改七遍非常浪费时间。”

“我们做的不是一个简单的复制粘贴工具，而是一套多平台内容适配和发布系统。用户只输入一次内容，系统会自动生成七个平台各自可用的版本，并支持模拟发布、辅助发布，以及真实自动化分发。”

## 4. 第一部分：输入一次，多端适配

操作：

1. 打开编辑器，展示左侧 Markdown 输入区。
2. 输入一段包含标题、列表、引用、图片、外链的示例内容。
3. 说明右侧多个平台实时预览会同步变化。

讲解词：

“这里左侧输入的是统一内容源，采用 Markdown。系统先把内容解析成中间表示 IR，再根据不同平台能力做自动降级和序列化。”

“右边可以看到多个平台已经不是同一份原样内容了，而是各自适配后的结果。比如公众号是内联 HTML，知乎是富文本粘贴格式，B站是受限 HTML，小红书会转成更适合发布的纯文本风格，掘金、博客园和 CSDN 则直接输出原生 Markdown。”

## 5. 第二部分：平台差异自动处理

操作：

1. 指向公众号预览。
2. 指向知乎预览。
3. 指向 B站预览。
4. 指向小红书预览。
5. 指向掘金预览。
6. 指向 CSDN 预览。

讲解词：

“公众号这边，系统会输出全内联样式 HTML，避免 class 和外链样式失效。”

“知乎这边，系统支持富文本粘贴链路，适合写文章编辑器。”

“B站专栏这边，会输出受限 HTML 子集，避免很多平台不支持的结构直接失真。”

“小红书这边最典型，它不是富文本优先，而是更偏纯文本表达，所以系统会生成更适合小红书风格的正文和话题结构，并支持封面预览。”

## 6. 第三部分：一键发布的三种模式

讲解词：

“这个项目不是只有一种发布方式，而是分三层能力，适合不同平台和不同风险承受能力。”

“第一层是默认的模拟发布。它最安全，适合答辩演示、团队联调和内容校验。”

“第二层是辅助发布。比如浏览器扩展会帮用户复制富文本，或者尽力注入到目标平台编辑器，但不会替用户乱点发布。”

“第三层是真实发布。公众号走官方 API，知乎、B站、小红书走 Playwright 本机自动化发布。”

## 7. 第四部分：公众号真实发布

如果演示公众号真实发布：

操作：

1. 打开设置面板。
2. 展示“公众号发布方式”。
3. 切到“创建公众号草稿”或“提交公众号发布”。
4. 点击发布。

讲解词：

“公众号是六个平台里最适合做官方接入的，因为它提供了正式 API。这里可以选择模拟发布、创建草稿，或者提交公众号发布。”

“真实发布时，前端不会接触 AppSecret，密钥只保存在本地 server。前端只构造 payload，server 再调用微信官方接口。这保证了安全边界。”

“如果因为 IP 白名单或者封面要求失败，系统会返回明确错误，而不是静默失败。”

## 8. 第五部分：Playwright 真实网页自动化分发

操作：

1. 打开设置面板。
2. 展示 “Playwright 真实分发” 区域。
3. 展示 `Runner 地址`。
4. 把知乎或小红书切到“全自动点击发布”。
5. 点击“一键发布”。

讲解词：

“知乎、B站、小红书没有稳定开放的普通发布 API，所以我们增加了本机 Playwright runner。它复用用户本机浏览器登录态，打开真实创作者中心，自动填写标题、正文、标签，并在显式开启后点击最终发布按钮。”

“这里有四种模式：模拟发布、辅助复制/注入、自动填写并保存草稿、全自动点击发布。这样用户可以按风险和需求自由选择。”

“注意这里的设计是克制的。系统不会保存平台账号密码，也不会绕过验证码、短信验证、人机验证。如果页面出现这些阻断，runner 会停下来并返回 `needs-user-action`，让用户接手处理。”

## 9. 第六部分：可扩展架构

操作：

1. 展示架构图或 README 中的 adapter 说明。
2. 指出 `core / app / server / runner` 四层。

讲解词：

“这个项目的关键不是只写死六个平台，而是做了一个可扩展架构。”

“`packages/core` 负责统一 IR、能力声明、格式变换和平台适配器。”

“`packages/app` 负责 Web 和扩展共用的一套 UI。”

“`packages/server` 负责公众号密钥、图床和官方 API 交互。”

“`packages/runner` 负责 Playwright 本机自动化分发。”

“如果后续接入更多平台，只需要新增 adapter 和对应的发布器，而不是重写整套系统。”

## 10. 收尾话术

“总结一下，这个项目解决的不是单一平台编辑问题，而是创作者多平台分发的效率问题。”

“它现在已经具备三类价值：第一，自动适配六个平台格式；第二，支持模拟、辅助和真实发布；第三，具备继续扩展更多平台的工程化架构。”

“对于商业化，它可以继续往创作者 SaaS、企业内容分发后台、MCN 运营工具三个方向延展。”

## 11. 演示兜底方案

如果真实平台网络或登录态不稳定，按这个顺序降级：

1. 先演示实时适配和多平台预览。
2. 再演示模拟发布回执。
3. 再展示设置里的公众号真实发布和 Playwright 真实分发配置。
4. 最后口头说明：真实平台联调依赖账号登录态和平台风控，本项目已具备工程接线和本机自动化能力。

## 12. 答辩常见问答

Q：为什么知乎、B站、小红书不直接走官方 API？

A：因为这些平台对普通开发者没有稳定开放的文章发布 API，所以我们采用本机 Playwright 自动化，复用真实网页登录态完成发布。

Q：为什么不把账号密码存进系统里？

A：这样做风险高，也容易越过平台合规边界。我们采用本机浏览器持久化 profile，只复用用户已有登录态。

Q：如果页面改版怎么办？

A：我们把平台自动化逻辑拆成独立 adapter 和 selector 层，页面改版时只需要调整该平台的自动化模块，不影响核心内容适配链路。

Q：为什么有模拟发布模式？

A：因为真实分发依赖外部平台、登录态、验证码和风控。模拟发布可以保证演示、测试、校验和内容生产流程稳定可复现。
